# Contracts - the fixed formats

## Candle data
Columns: time, open, high, low, close. "time" is UTC.
(TO CHECK: confirm the data loader really uses these names.)
- Timeframe is explicit candle metadata, not inferred from gaps. Supported codes are M1, M5, M15, M30, H1, H2, H4, D1, and W1. A candle covers its opening time up to (but not including) the next timeframe boundary; its closing price is only known after that boundary.

## Candle-data quality
- Report invalid, duplicate, and out-of-order timestamps; missing columns; non-finite or non-positive prices; malformed OHLC candles; and zero-range candles.
- Report intervals longer than the selected candle timeframe. Weekend-shaped gaps are shown separately, but gaps are not automatically called bad data because market closures and holidays must be distinguished from missing feed data.
- List the largest candle ranges and close-to-close moves as candidates for manual review. Do not mark a price as bad using an unverified threshold.

## Time
Everything inside the bot is UTC. South African time (Africa/Johannesburg) is only for the screen and reports.

## Live market data feed
- The cTrader feed is data-only: it publishes bid/ask quotes and completed M1 and M5 candles and does not send orders.
- The API starts the Demo feed by default. Set `CTRADER_ENV=demo` or `CTRADER_ENV=live` to choose the matching cTrader account environment; the API supports both market-data endpoints and sends no orders. Set `CTRADER_FEED_ENABLED=false` to disable the feed.
- Feed timestamps are UTC. Mutable M1 and M5 candles stay internal until a later candle of the same timeframe starts; callbacks receive only the completed candle. An unfinished candle is discarded on disconnect.
- Credentials are validated before connecting and are never logged. FastAPI exposes the latest quote and completed M1/M5 candles to the screen; the feed is not connected to strategies or order execution.
- The live feed retains up to 10,080 completed candles per timeframe in memory from the time the process connects; it does not backfill historical candles. Reports that need more history or other timeframes must say they are unavailable or still warming up.
- The cTrader client requests broker balance and leverage plus each position's net unrealized PnL every 30 seconds. `/api/account/facts` reports the deposit-asset ID and calculated equity (`balance + net unrealized PnL`) with separate local receipt times; data older than 60 seconds is unavailable. cTrader reports leverage in hundredths and monetary values using `moneyDigits`; calculated equity excludes potential closing commissions and is not a direct broker-reported equity value. Account history and detailed positions remain unavailable rather than returning samples or claiming an empty account. Live broker account retrieval and connection are not yet verified.

## One-minute market snapshots
- A market snapshot is queued when a completed M1 candle arrives and calculated on a single background worker so report calculations do not block feed callbacks. It uses the latest quote and up to 1,000 most recent completed M1/M5 candles for each timeframe's reports. Previous-day/week level reports can use the retained M1 history. The API exposes the latest completed report at `/api/market/snapshot`; it is unavailable until the first report finishes. The Dashboard checks this endpoint every five seconds and keeps market reports, indicator reports, and unavailable inputs separate.
- The snapshot reports each available knowledge/indicator observation separately. It does not combine them into a score, approve a trade, or evaluate entry criteria. Missing source data and required inputs are reported as unavailable; draft or unverified component conventions remain unverified.
- Snapshot updates every minute are context refreshes, not entry checks. Entry criteria are a separate future feature and are not implemented now. Their future evaluation frequency must follow the chosen strategy's actual trigger rule; the latest minute snapshot can provide context between 5-minute candle closes, but it does not make an unfinished M5 candle complete or prove a breakout.

## Names
File names are lowercase_with_underscores. Imports must match the file names exactly.

## Test organization
- Keep production code and tests in separate folders. Put tests under `trading-engine/tests/<area>/`; for example, knowledge tests belong in `tests/knowledge/`, separate from `knowledge/` source files.
- Indicator tests belong in `tests/indicators/`, separate from reusable calculations in `indicators/`.
- Keep each test module focused on its corresponding concept and name it `test_<concept>.py`. Do not add test files beside production modules.
- `pytest.ini` limits discovery to the central `tests/` tree and configures the local import paths needed by the news-feed tests.

## Indicators
Indicator modules calculate or report values from supplied data. They do not select entries or issue trade signals.
- `indicators/exponential_moving_average.py` reports EMA 20, 50, 100, and 200 from completed close prices at an explicit supported timeframe. It seeds each recursive EMA from the first supplied close, so results depend on supplied history and can differ from TradingView if its chart has more history. It reports indicator values only, not crossovers or trade signals.
- `indicators/pivot_points.py` calculates the Traditional pivot formula from caller-supplied high, low, and close values for the previous completed pivot period. Chart mapping is M1/M5/M15/M30/H1/H2 to daily, H4 to weekly, D1 to monthly, and W1/monthly to yearly. It does not fetch or aggregate the prior period; the strategy or market-data caller must supply those values.
- `indicators/fibonacci_retracement.py` calculates price levels between two caller-supplied points using configurable ratios, with optional logarithmic interpolation. The defaults are 0%, 23.6%, 38.2%, 50%, 61.8%, 78.6%, and 100%; the caller chooses the points and may supply other ratios, including extensions. These are calculation defaults, not proven strategy levels. It does not select swing points or assign trading meaning to levels.
- `indicators/anchored_vwap.py` calculates cumulative price-times-volume divided by cumulative volume for caller-supplied ordered values starting at an anchor. The caller selects the anchor, price source, and volume source. The current candle contract has no volume column, so an integrating caller must provide verified volume data; candle range is not a substitute.

## Knowledge files
Knowledge files turn the relevant price feed and context into plain-language observations the later strategy and risk-management stages can use. Each file stays focused on one concept and reports what it found, including relevant direction, price levels, and time. If the required data is missing, the result must say so rather than guess.
- Knowledge observations are information for later stages. They do not approve trades, choose a position side, set risk size, or place or move orders.
- Candlestick anatomy reports candle direction, body, wicks, range, and configured candle-pattern labels. It can analyze one candle; multi-candle patterns require enough closed candles. It does not choose a long or short trade.
- Market direction (bullish, bearish, or ranging) describes price conditions. Position side (long or short) describes an actual trade. A market-direction label never creates a position; BUY and SELL map to LONG and SHORT only on a trade record.
- Market-structure labels are descriptive conventions: confirmed swing highs/lows are compared using the configured left/right candle lookback. A swing is not available until its right-side confirmation candles have closed; ranging means the latest swing labels do not meet the module's bullish or bearish pattern.
- `knowledge/support_resistance.py` reports confirmed swing highs as candidate resistance and swing lows as candidate support, including price and timestamps. It does not merge levels into zones or claim that a level will hold.
- `knowledge/supply_demand.py` reports the full high-to-low range of each completed candle that forms a confirmed swing high or low as a candidate supply or demand zone. This is a simple geometric convention, not a mentor-verified zone definition; it does not merge zones, claim hidden orders, or predict a reaction.
- The current market-structure break labels use the configured close-or-wick rule and classify continuation breaks as BOS, otherwise CHOCH. These are one convention, not a mentor-confirmed strategy rule. MSS has no separate detector yet because its definition overlaps with CHOCH and varies between sources.
- Fair value gaps are detected by the first candle's high being below the third candle's low (bullish) or the first candle's low being above the third candle's high (bearish). A configurable ATR-size filter and fill criterion affect which gaps/statuses are reported; these settings are conventions, not confirmed strategy rules. Reports include gap bounds, midpoint, creation time, and status.
- Inverse fair value gaps are reported when a configured close-or-wick rule crosses the original gap's far edge. Reports include original bounds, new direction, inversion time, retest time, and fresh/retested/failed status. These definitions are configurable conventions, not confirmed strategy rules.
- Liquidity pools are reported from clustered confirmed swing highs/lows using a configurable ATR tolerance. Equal highs are labeled buy-side pools; equal lows are labeled sell-side pools. Sweep/break status depends on configured wick/close rules and is descriptive only; it is not proof of actual resting orders.
- Equilibrium is the 50% midpoint of an explicit, swing-based, or previous-UTC-day range. Premium/discount describe price above/below that midpoint. Optional 25%/75% quartiles are reported as price levels only; they are not labeled "optimal" or used as trading advice.
- Trend-line reports use the two latest confirmed swing highs or lows in each supplied timeframe and project that straight line to the latest candle time. They are geometric candidates; no line-strength, touch, or break rule is implied.
- Stop-loss, take-profit, and break-even facts depend on an existing trade or supplied level context. Raw prices alone cannot reveal which stop or target a trader intends. A knowledge file may report supplied levels and their relation to prices, but must not invent placement or break-even-move rules.
- `knowledge/stop_loss.py` receives a position side, supplied stop-loss price, bid/ask, and UTC quote time. It reports whether the correct quote side has reached or passed that level; it does not confirm a broker fill or place/move a stop.
- `knowledge/take_profit.py` receives a position side, supplied take-profit price, bid/ask, and UTC quote time. It reports whether the correct quote side has reached or passed that level; it does not confirm a broker fill or close a position.
- `knowledge/break_even.py` receives the entry, stop, broker tick size, position side, bid/ask, and UTC quote time. It reports whether the stop and quote are at the entry tick. This is a price comparison, not a net-profit guarantee, and it never moves the stop.
- `knowledge/spread.py` reports ask minus bid and the UTC quote time. Pip and tick conversions are included only when their sizes are supplied; it does not judge whether the spread is acceptable for a strategy.
- `knowledge/drawdown.py` reports the amount and percentage that supplied account equity is below its supplied peak, including the current and largest observations in the supplied history. Opening equity may be supplied as the initial peak; the report cannot include peaks outside the history it receives and does not set a risk limit.
- `knowledge/timeframes.py` reports the UTC time window represented by an explicitly labeled candle timeframe. It does not infer a timeframe from candle gaps or treat an unfinished candle's final price as available.
- `knowledge/multi_timeframe_alignment.py` compares confirmed market-structure reports from explicitly supplied timeframes, using only candles whose timeframe window ended by the supplied UTC observation time. Alignment is bullish or bearish only when every available timeframe reports that state; mixed/ranging results are reported as mixed, and fewer than two available timeframes are not assessed. This is not a trade decision.
- `knowledge/weekly_bias.py` reports the existing market-structure state from completed W1 candles, the latest reported weekly structure break, and whether completed D1 structure aligns. It uses the configured swing and close-or-wick conventions without adding weighted evidence, trade sizing, or entry rules; those conventions are not mentor-verified.
- `knowledge/round_numbers.py` reports the configured price interval's lower and upper levels around a supplied quote. The interval must be provided for each instrument; round numbers are not claimed to be support, resistance, or trade targets.
- `knowledge/break_retest.py` checks an explicitly supplied price level, bullish/bearish direction, close-or-wick break rule, and retest tolerance. It reports a crossing and any later candle-range touch; it does not claim the level held or call the pattern a trade setup.
- `knowledge/previous_day_levels.py` reports the observed high and low from supplied, completed candles fully contained within the prior UTC calendar day. It reports no levels when data is missing and warns that gaps may hide the true extremes.
- `knowledge/previous_week_levels.py` reports the observed high and low from supplied, completed candles fully contained within the previous Monday-to-Sunday UTC calendar week. It requires an explicit supported timeframe, excludes candles crossing the week boundary, reports no levels when data is missing, and warns that gaps may hide the true extremes. It does not identify a trade target.
- `knowledge/economic_calendar.py` reads local monthly and latest-run snapshots, converts event times from their recorded source timezone to UTC, and reports whether the most recent snapshot is fresh, stale, unknown, or unavailable. The control center's Economic Calendar page links to the free Forex Factory calendar website. It does not download or display calendar events inside the app because no official free API or permission for automated access has been verified. The bot's local news-report component remains separate and can only report files already supplied to it; no paid calendar provider or API key is required.
- `knowledge/time_structure.py` reports the Asia, London, New York, and overlap session label plus the configured London/New York killzone clock windows, with daylight-saving-aware local times. These boundaries are code configuration and do not prove which hours have the most trading volume.
- `knowledge/daily_bias.py` already reports a bullish, bearish, or neutral daily bias using weighted daily structure, previous-day close location and candle anatomy, liquidity, and fair-value-gap evidence. Its weights, thresholds, evidence interpretations, and invalidation level are not verified mentor rules; do not silently change them or treat the result as proven. `knowledge/weekly_bias.py` separately reports weekly structure and daily alignment using only completed candles; it does not alter daily-bias scoring or decide whether to trade.
- `knowledge/average_candle_range.py` requires an explicitly supplied supported timeframe, a positive lookback count, and a UTC observation time. It averages high minus low for the most recent supplied candles whose timeframe windows have completed by that time. The report includes the requested and actual sample counts and states when fewer candles were available; it reports raw price units and does not infer pips, ticks, or volume. `knowledge/average_daily_range.py` provides the D1-specific report using this same calculation. Candle range describes price movement, not traded volume. Do not label a large range as high volume; report broker-supplied volume separately only after its meaning and units are verified.
- The backtest simulator's ATR-based stop and target levels are simulator mechanics driven by strategy inputs; they are not general knowledge rules for placing stops or targets.
- `risk_management.py` checks an explicitly supplied proposed loss against required per-trade, daily-loss, daily-trade-count, and open-position limits. Master-strategy ceilings are 2% risk per trade and two trades per day; callers may set lower strategy-specific limits, including one trade per day. It returns UNKNOWN when account state or planned loss is missing, never supplies default risk limits, and does not place orders. The planned loss must already include the relevant instrument and cost calculations.
- `broker/lot_sizing.py` calculates volume from supplied equity, risk percent, entry/stop prices, contract value, and broker volume limits. It supports explicit tick size/value inputs or a direct price-value-per-lot input and rounds down to the broker step. `broker/ctrader_symbol_specs.py` converts cTrader's `lotSize`, `minVolume`, `stepVolume`, and `maxVolume` fields from protocol cents into units for the current EURUSD feed. It only supplies price value when the symbol quote asset matches the account deposit asset; other currency conversions remain unavailable. If cTrader reports `maxExposure`, sizing is refused until existing exposure can be included. A broker symbol-change event invalidates the cached specifications until the updated details arrive. `/api/broker/lot-size` requires fresh broker equity, complete symbol specifications, entry, stop loss, and risk percent; it reports a size and does not place an order. The calculation does not include spread, commission, or slippage, and live broker retrieval remains unverified.

## Strategy evaluations
- Each implemented strategy check lives in its own `strategies/<strategy_name>/` folder. A trigger evaluation is not an order and does not bypass risk management.
- A core trigger is required before confluence is considered. Confluence facts may support a trigger but cannot start one by themselves; suggested group-count thresholds are not defaults.
- Conflicting versions stay separately named and are never selected by default. Missing trigger definitions, data, stop rules, target rules, or required filters block an evaluation instead of being guessed.
- `strategies/pivot_break_retest/` currently implements only the daily S1/R1 break-and-retest candidate, targeting S2 after an S1 break or R2 after an R1 break. The caller supplies completed candles, daily pivot levels, other confluence facts, the narrow-range observation, and a stop beyond the pivot on the risk side. A close back across the pivot invalidates the prior break. The evaluator reports a candidate only; it does not place or manage a trade.
- The master strategy document is an AI compilation and remains unverified. Rules tagged as variants, suggestions, or gaps are not proven; the backtester remains unverified and is not connected to these strategy evaluations.

## Backtester behavior (project goal; prototype implemented but unverified)
- Historical backtests replay timestamped broker data in order. The selected history period should be configurable (for example, about one year).
- Historical, demo-forward, and live processing use the same causal strategy and account rules. Each decision and fill may use only prices and information available at that time. Live processing responds to incoming updates at the feed's available frequency; an unfinished candle must not expose its eventual high, low, or close.
- A validated signal is executed using the next available realistic price, not a price chosen later with knowledge of what happened next. Ambiguous cases, such as a candle touching both stop loss and take profit, must have an explicit, tested rule.
- Track the initial deposit separately from later deposits or withdrawals. Keep the account balance (realized results) and equity (balance plus open-trade profit or loss) over time, including daily changes and return from the initial deposit.
- Update account results after every fill and trade close. Once risk management is implemented, each new trade must use the current account state under an explicitly documented risk policy, so previous gains and losses affect later sizing. Do not invent the risk formula before it is decided.
- Apply configured spread, commission, slippage, and overnight costs consistently to simulated fills and account results; do not silently omit costs.
- Treat backtest results as untrusted until tests verify that no future information is used and that fills, costs, balance, and equity are calculated correctly.

### Current prototype limits
- Runs offline on one symbol (EURUSD), one timeframe (H1), and the local historical candle file. It does not connect to a live feed.
- Calls strategies only after a bar closes, passes only the history available through that close, and enters at the next bar's open.
- Requires risk percent as an input; the first example run uses 2% of current equity. Position size is rounded down to the lot step, and trades below the minimum lot are skipped.
- Tracks balance and marked-to-market equity. It currently allows only one open trade and does not model deposits, withdrawals, margin, leverage limits, or overnight swap.
- Uses fixed spread, commission, and slippage assumptions. If a bar touches both stop and target, stop loss wins. A price gap can exceed the planned risk.
- Produces a separate candle-data quality report. The current EURUSD H1 file has no structural timestamp/OHLC errors, but has long intervals and extreme candle ranges that still need source verification.
- Results are labeled unverified. Strategy validation, live-feed parity, advanced risk limits, and research metrics remain incomplete.
